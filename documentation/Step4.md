**Crylo — Step 4: Pre-Provision, IaC Generation & Provisioning**

**Overview**

Step 4 takes the finalized canvas.yml and intent record and produces a running AWS infrastructure. It is divided into four phases: AWS account connection, environment variable collection, IaC generation and review, and provisioning. The user makes no architectural decisions in this step — those are locked. The only inputs required are AWS access and secret values for detected environment variables.

**Inputs to Step 4**

| **Input** | **Source** | **Used For** |
| --- | --- | --- |
| Finalized canvas.yml | Step 3 DB | IaC generation — what to build |
| Intent record | Step 2 DB | IaC generation — how to configure it |
| Env vars record | Step 1 DB | Identifying which values to collect |

**4.1 — AWS Account Connection**

**Method: IAM Role via CloudFormation Bootstrap Stack**

Crylo never asks for an access key or secret key. Long-lived IAM user credentials are a security liability — they never expire and if leaked give permanent admin access to the user's account. The correct pattern is a cross-account IAM role with short-lived assumed credentials.

**Flow:**

Crylo generates a pre-signed CloudFormation stack URL unique to the user's project. The UI presents a single button:

*"Connect your AWS Account"*

Clicking it opens the AWS CloudFormation console in a new tab with the stack pre-loaded. The user clicks **Create Stack**. The stack takes approximately 30 seconds to complete and creates:

* An IAM Role with a least-privilege policy scoped to exactly what Crylo needs to provision
* A trust policy that only permits Crylo's AWS account ID to assume the role
* Nothing else

Once the stack completes, the role ARN is returned to Crylo via a CloudFormation output. The user pastes this ARN into the Crylo UI, or Crylo detects it automatically if the user granted read access to CloudFormation outputs.

From this point, whenever Crylo needs to act in the user's account it calls sts:AssumeRole to get short-lived temporary credentials. These credentials expire in one hour and are never stored in Crylo's database.

**Why this is better:**

* No long-lived credentials ever leave the user's AWS account
* Role can be deleted at any time to immediately revoke Crylo's access
* Same pattern used by Terraform Cloud, Pulumi, and AWS CDK Pipelines
* Technical users will recognise and trust it immediately

**4.2 — Environment Variable Collection**

After AWS connection, the user is shown a clean variable input form. This is the only form in the entire Crylo flow.

**What is shown:**

All variables from the Step 1 env vars record are displayed, grouped by classification:

**Group 1 — Values required from you**

These are user\_secret vars — Crylo detected them but cannot generate their values:

SECRET\_KEY Django's cryptographic signing key

STRIPE\_SECRET\_KEY Your Stripe integration

SENDGRID\_API\_KEY Your email service

Each entry shows the key name and a plain English description of what it's for. The user pastes the value. Fields are masked by default (password input).

**Group 2 — Auto-generated by Crylo**

These are generated vars — shown for transparency but not editable. The user can see that Crylo will handle them:

DATABASE\_URL ✓ Generated from your RDS instance

REDIS\_URL ✓ Generated from your ElastiCache cluster

CELERY\_BROKER\_URL ✓ Generated from your SQS queue

AWS\_S3\_BUCKET\_NAME ✓ Generated from your S3 bucket

**Group 3 — Additional variables**

A simple "Add variable" option at the bottom. The user can add any key/value pair Crylo didn't detect. This covers edge cases — a third-party API key that lives deep in the codebase rather than in settings.py, for example.

**Storage:**

All user-provided values are written directly to AWS Secrets Manager in the user's account via the assumed role. They are never stored in Crylo's database. Not in logs. Not in transit beyond the single write call. Crylo stores only the key names and their Secrets Manager ARNs.

**4.3 — IaC Generation**

Once AWS is connected and env vars are collected, Crylo generates the CloudFormation template. This happens entirely in the background — the user sees a brief loading state.

**Inputs to the generator:**

canvas.yml (finalized) → what resources exist, aws\_service per node, connections

intent record → instance sizes, multi-AZ, environment, domain config

**What the generator produces per canvas node type:**

type: service (ecs\_fargate)

→ AWS::ECS::TaskDefinition

→ AWS::ECS::Service

→ AWS::IAM::Role (task execution role)

→ AWS::Logs::LogGroup

→ AWS::EC2::SecurityGroup

→ AWS::ElasticLoadBalancingV2::LoadBalancer

→ AWS::ElasticLoadBalancingV2::TargetGroup

→ AWS::ElasticLoadBalancingV2::Listener

type: service (ec2)

→ AWS::EC2::Instance

→ AWS::EC2::SecurityGroup

→ AWS::IAM::InstanceProfile

→ AWS::ElasticLoadBalancingV2::LoadBalancer

→ AWS::ElasticLoadBalancingV2::TargetGroup

→ AWS::ElasticLoadBalancingV2::Listener

type: static (s3\_cloudfront)

→ AWS::S3::Bucket

→ AWS::CloudFront::Distribution

→ AWS::CloudFront::OriginAccessControl

type: database (rds\_postgres)

→ AWS::RDS::DBInstance

→ AWS::RDS::DBSubnetGroup

→ AWS::EC2::SecurityGroup

→ AWS::SecretsManager::Secret (credentials)

**Networking — derived from canvas connections:**

The connection graph in canvas.yml drives all security group rules. No manual configuration required.

connection: backend → db

→ Ingress rule on db security group: port 5432 from backend security group

connection: backend → cache

→ Ingress rule on cache security group: port 6379 from backend security group

connection: backend → worker

→ Both share the same VPC, worker pulls from SQS — no direct ingress needed

connection: frontend → backend

→ ALB listener on 443, target group pointing to ECS service

**VPC and subnet configuration — derived from intent:**

criticality: high

→ Multi-AZ: 2 public subnets, 2 private subnets across 2 AZs

criticality: low | medium

→ Single-AZ: 1 public subnet, 1 private subnet

All resources except ALB and CloudFront → private subnets

ALB → public subnet

RDS, ElastiCache → private subnet, no public access

**Domain and ACM — derived from intent:**

intent.domain.has\_domain: true

→ AWS::CertificateManager::Certificate (DNS validation)

→ ALB HTTPS listener on 443

→ HTTP to HTTPS redirect on 80

→ Output: CNAME record for user to add to their DNS

intent.domain.has\_domain: false

→ ALB HTTP listener on 80 only

→ Output: ALB DNS name

**Environment naming convention — derived from intent:**

intent.environment: production → {project}-prod-{resource}

intent.environment: staging → {project}-staging-{resource}

intent.environment: development → {project}-dev-{resource}

**4.5 — Provisioning**

On clicking Provision, Crylo submits the CloudFormation template to the user's AWS account via the assumed role and opens a live deployment screen.

**Live deployment feed:**

Not a spinner. A real-time log of CloudFormation stack events, translated to plain English with status indicators:

✅ VPC created

✅ Subnets configured (2 public, 2 private)

✅ Security groups created

✅ SQS queue ready

✅ ECR repository created

⏳ RDS instance starting — this typically takes 3–5 minutes...

✅ ElastiCache cluster ready

✅ ECS cluster created

✅ ECS task definitions registered

⏳ ECS services starting...

✅ ECS services healthy

✅ CloudFront distribution deployed

✅ ACM certificate validated

✅ Load balancer ready

Each item shows a timestamp. Estimated time remaining is shown at the top of the feed. Current average for a full stack: 8–12 minutes, dominated by RDS startup time.

**Error handling:**

If any CloudFormation resource fails, the feed shows the failure clearly in plain English with a suggested resolution:

❌ RDS instance failed to create

Reason: Insufficient capacity for db.t3.medium in us-east-1a

Resolution: Crylo will retry in us-east-1b automatically

Crylo attempts automatic resolution for known failure types before surfacing an error to the user. Unknown failures surface with the raw CloudFormation error and a link to contact support.

**4.6 — Success**

When provisioning completes, a clean success screen:

**Outputs:**

✅ Your app is live

Frontend URL https://app.myproduct.com

Backend API https://api.myproduct.com

CloudFront URL https://d1234abcd.cloudfront.net

Next steps:

→ Add this CNAME to your DNS: app.myproduct.com → d1234abcd.cloudfront.net

→ Set up your CI/CD pipeline to push to ECR on merge to main

→ Your architecture is saved and visualized in your canvas

The canvas transitions to a read-only **live architecture** mode. The diagram now represents deployed, real infrastructure. Any future changes require creating a new version.

**4.7 — What Step 4 Does Not Do**

* Does not store environment variable values in Crylo's database — only in AWS Secrets Manager
* Does not ask any architectural questions — those are locked after Step 3
* Does not modify canvas.yml or the intent record
* Does not set up CI/CD pipelines — out of scope for MVP
* Does not configure monitoring or alerting — out of scope for MVP

**Step 4 Outputs**

| **Output** | **Location** | **Consumer** |
| --- | --- | --- |
| Deployed CloudFormation stack | User's AWS account | Live infrastructure |
| Stack outputs (URLs, ARNs) | DB + displayed to user | Success screen, canvas |
| Provisioning log | DB | Audit, debugging |
| Secrets Manager entries | User's AWS account | Runtime env vars |
