# CLYRO.md: Offline Agent Repo Scan Brainstorm

> **Status note added 2026-09-06. This is a brainstorm, kept for the options it
> weighed, not a description of anything.** The idea won and shipped: see
> [Chapter 20](ch_20_offline_scan_contract_plan.md) for the plan and
> [Chapter 8](ch_8_wizard_step_1_connect.md) for how Step 1 works now.
>
> Read the "Current Architecture" section as a description of the system this
> replaced. `deterministic_detector.py` and the RepoRecon AgentCore agent are both
> deleted, and there are only two AgentCore runtimes left, neither of them
> RepoRecon.
>
> Where the document proposes and what was actually chosen:
>
> - **The `derivable` classification was not adopted.** The shipped enum in
>   `app/scanner/clyro_md.py` is `generated`, `optional`, `user_secret`, with a
>   `hint` of `agent_generatable` or `third_party` on the last of those.
> - **The CLI package (option D) was not built.** The skill-only path (option A)
>   shipped, installed to `~/.claude/skills/clyro-scan/`, not to the
>   `~/.gemini/...` path this document guesses at.
> - **There is no fallback to a live scan when `CLYRO.md` is absent.** Chapter 20
>   rejected that explicitly: the live scan path is deleted, not kept in reserve. A
>   missing contract is a retryable block with setup instructions.
> - **There is no canvas seed.** The contract carries none, and
>   `ScanResult.draft_canvas_yaml` is written by nothing and read by nothing.
> - **The `clyro/validate-action@v1` GitHub Action in section 9 was not built.**
>
> Its wizard step numbers are the retired five-step scheme. Secrets are collected in
> **Step 1**, intent questions are **Step 3**, domain is asked in **Step 3**, the
> canvas is **Step 4**, IaC generation is **Step 5**, and the build runs during
> **Step 6**.

## The Core Idea

Replace Step 1's live, cloud-based RepoRecon scan with an **offline agent** (an AI coding agent like Claude Code, Cursor, Aider, etc.) that the user runs locally against their repo. The agent reads a prompt/skill and produces a single `CLYRO.md` file at the repo root. This file becomes the **single source of truth** that the Clyro platform ingests to skip or radically simplify Step 1.

The file needs to carry **everything** Step 1 currently produces, but in a format that's:
- Human-readable (Markdown) so devs can review/edit it
- Machine-parseable so the Clyro backend can ingest it
- VCS-friendly so it lives in the repo and is visible in PRs

## Ideas for How This Can Work

### 1. The Skill/Prompt Approach

Create a **Clyro Skill** (like graphify's `SKILL.md`) or a downloadable prompt that any coding agent can execute:

```
/clyro-scan              # runs the scan, writes CLYRO.md
/clyro-scan --fix        # also auto-fixes compliance failures
/clyro-scan --validate   # checks an existing CLYRO.md against the repo
```

**Pros**: Works with Claude Code, Cursor, Aider, Windsurf — any agent with file access.  
**Cons**: Different agents might produce slightly different outputs; schema fidelity matters.

### 2. The Deterministic-First, Agent-Second Hybrid

The offline agent itself mirrors the [deterministic_detector.py](../backend/app/scanner/deterministic_detector.py) pattern:

1. **Phase 1 (Deterministic)**: A script/CLI runs locally — reads `requirements.txt`, `package.json`, settings files, Dockerfiles. Produces a partial `CLYRO.md` with everything it can confidently detect.
2. **Phase 2 (Agent)**: The AI agent fills in gaps — `wsgi_path`, `project_name`, ambiguous env var classifications, checks the agent can't do mechanically (e.g., "is this env var actually needed in production?").

This is what the current system already does (deterministic_detector → RepoRecon fallback), but **moved to the user's machine**.

### 3. Secret Classification — The Two-Bucket System

Your instinct to split secrets into two types is exactly right. The current [EnvVarKey.Classification](../backend/core/models.py) already does this:

| Classification | Current Name | Who Provides | Examples |
|---|---|---|---|
| `generated` | Auto-provisioned | Clyro creates these during deploy | `DATABASE_URL`, `CELERY_BROKER_URL`, `AWS_STORAGE_BUCKET_NAME` |
| `user_secret` | User must provide | User enters in Step 6 (SecretsWrite) | `STRIPE_SECRET_KEY`, `SENDGRID_API_KEY`, `DJANGO_SECRET_KEY` |
| `optional` | Safe to skip | Has a safe production default | `DEBUG`, `ALLOWED_HOSTS` |

**New ideas for the CLYRO.md expansion**:

- **`agent_generatable`** (new): Secrets the agent can *create* for the user right now (e.g., `DJANGO_SECRET_KEY` — just needs a random 50-char string). The agent writes it to CLYRO.md or a companion `.env.clyro` file.
- **`derivable`** (new): Secrets that can be derived from other infrastructure (e.g., `REDIS_URL` is derived from the ElastiCache endpoint Clyro provisions).
- **`third_party`** (new): Secrets from external services the user must go get themselves (Stripe dashboard, SendGrid console, etc.) — with **links** to where to get them.

So the full taxonomy becomes:

```
┌─────────────────────────────────────────────────────┐
│              Environment Variables                   │
├──────────────┬──────────────────────────────────────┤
│ Agent Can    │ • generated (Clyro infra provisions) │
│ Handle       │ • agent_generatable (random/derived) │
│              │ • derivable (from other infra)       │
│              │ • optional (safe defaults)           │
├──────────────┼──────────────────────────────────────┤
│ User Must    │ • user_secret / third_party          │
│ Provide      │   (with links to where to get them)  │
└──────────────┴──────────────────────────────────────┘
```

### 4. CLYRO.md as a Living Contract

> [!IMPORTANT]
> The most powerful idea: CLYRO.md isn't just a scan output — it's a **contract** between the user's repo and the Clyro platform.

- **User edits**: The user can manually override any detection. Got a custom WSGI setup? Edit the `wsgi_path`. Using a non-standard Dockerfile location? Fix the `path`. The agent's scan is the *starting point*, not the final word.
- **Version-controlled**: Lives in the repo, shows up in PRs. When someone adds a new env var, the CI or a pre-commit hook could warn: "This env var isn't in CLYRO.md — run `/clyro-scan --update`."
- **Diffable**: Because it's Markdown+YAML, changes are human-reviewable in `git diff`.
- **Schema versioned**: The `<!-- Schema version: 1 -->` comment lets the Clyro backend handle backwards compatibility.

### 5. Ingestion on the Platform Side

When the user hits "Deploy" or connects their repo:

```
┌──────────┐     ┌──────────────┐     ┌──────────────────┐
│ User's   │────▸│ Clyro reads  │────▸│ Skip Step 1 UI   │
│ Repo has │     │ CLYRO.md via │     │ entirely, go     │
│ CLYRO.md │     │ GitHub API   │     │ straight to      │
│          │     │              │     │ Step 2 (Intent)  │
└──────────┘     └──────────────┘     └──────────────────┘
```

- **CLYRO.md present + valid**: Ingest it, populate `ScanResult` and `EnvVarKey` models directly, skip the scan entirely. Show the user a "Review Scan" card (not a "Scanning..." spinner).
- **CLYRO.md present + stale**: Warn the user ("CLYRO.md was generated 30 days ago, repo has changed — rescan?").
- **CLYRO.md absent**: Fall back to the current Step 1 flow (deterministic + RepoRecon agent).

### 6. The `--fix` Mode

The offline agent doesn't just *detect* compliance issues — it **fixes them**:

```bash
# In user's local repo, using their coding agent
> /clyro-scan --fix

✅ Added health endpoint to urls.py
✅ Changed Dockerfile FROM to ECR mirror
✅ Generated DJANGO_SECRET_KEY (added to .env.clyro)
⚠️  STRIPE_SECRET_KEY — you need to get this from https://dashboard.stripe.com/apikeys
⚠️  SENDGRID_API_KEY — you need to get this from https://app.sendgrid.com/settings/api_keys

Wrote CLYRO.md (5 resources, 8 env vars, 6/6 compliance checks passing)
Wrote .env.clyro (1 generated secret — do NOT commit this file)
```

This is possible because [compliance.py](../backend/app/scanner/compliance.py) already has `fix_hint` on every finding — the agent can read those hints and *apply them*.

### 7. Additional Sections CLYRO.md Could Carry

Beyond what Step 1 currently generates:

| Section | Purpose | Saves Which Step? |
|---|---|---|
| **Intent Hints** | "This is a production SaaS app, PostgreSQL, Redis for caching + Celery broker" | Step 2 (user doesn't need to answer intent questions) |
| **Canvas Seed** | Pre-populated `draft_canvas_yaml` | Step 3 (canvas starts pre-filled) |
| **Domain Info** | Custom domain, SSL preferences | Step 4 config |
| **Cost Estimate** | Based on detected resources, estimated AWS monthly cost | Shown in review |
| **Deployment Preferences** | Region, instance sizes, scaling rules | Step 4 IaC generation |
| **Test Commands** | How to run the project's test suite | Post-deploy verification |
| **Build Customizations** | Custom build commands, env-specific build args | Step 4 build |

### 8. Companion Files (Beyond CLYRO.md)

```
.clyro/
├── CLYRO.md              # Main contract file
├── .env.clyro            # Agent-generated secrets (gitignored)
├── resources.json        # Machine-parseable version of detected_resources
├── compliance.json       # Machine-parseable compliance findings
└── canvas-seed.yaml      # Pre-populated architecture canvas
```

**Or** keep it all in one `CLYRO.md` with embedded YAML/JSON blocks — simpler, but the file gets big. The single-file approach is probably better for v1.

### 9. Validation / Drift Detection

A CI-side check (GitHub Action or pre-commit hook):

```yaml
# .github/workflows/clyro-validate.yml
name: Validate CLYRO.md
on: [push]
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: clyro/validate-action@v1
        # Checks:
        # - CLYRO.md schema is valid
        # - env vars in CLYRO.md match what the code actually uses
        # - requirements.txt/package.json haven't added new deps that change the resource graph
        # - No new unclassified secrets
```

### 10. Distribution Mechanism for the Prompt

How does the user get the scan prompt/skill?

| Option | Mechanism | Pros | Cons |
|---|---|---|---|
| **A. Clyro Skill** | `~/.gemini/config/skills/clyro-scan/SKILL.md` | Works with Claude Code natively, versioned | Only works with Claude Code |
| **B. Cursor Rule** | `.cursor/rules/clyro-scan.md` | Works with Cursor | Only Cursor |
| **C. Universal Prompt** | Download from clyro.dev, paste into any agent | Works with anything | Manual, no auto-updates |
| **D. CLI Tool** | `npx @clyro/scan` or `pip install clyro-scan` | Agent-agnostic, deterministic | Needs a maintained package |
| **E. MCP Server** | Clyro MCP that any agent can call | Universal, structured I/O | MCP adoption still early |

**Recommendation**: Start with **D (CLI)** for the deterministic part + **A (Skill)** for the agent-augmented part. The CLI handles what [deterministic_detector.py](../backend/app/scanner/deterministic_detector.py) does today. The skill handles the LLM reasoning parts.

## Open Questions

1. **Should CLYRO.md be committed?** Yes — it's the contract. But `.env.clyro` should be gitignored.
2. **What if the user edits CLYRO.md incorrectly?** The platform-side ingestion should validate against a JSON schema and surface parse errors clearly.
3. **How does this interact with re-scans?** `--update` mode: re-run the scan, diff against existing CLYRO.md, show the user what changed.
4. **Multi-framework support?** Today Clyro only supports Django+React. CLYRO.md's schema should be extensible for future frameworks without breaking v1 consumers.
5. **Security**: CLYRO.md itself should **never** contain secret values — only key names and classifications. Actual values go in `.env.clyro` (gitignored) or are entered in the platform UI.

## Summary: What Changes

```
BEFORE (Today):
  User connects repo → Clyro's cloud scans it (17-41s) → Results in DB → UI shows them

AFTER (Proposal):
  User runs offline agent → CLYRO.md in repo → User connects repo → 
  Clyro reads CLYRO.md (instant) → Results in DB → UI shows them (pre-populated)
```

The win: **zero cold start, user has full visibility and control over what gets detected, compliance issues can be fixed before the user ever opens Clyro, and third-party secret instructions are right there in the repo.**
