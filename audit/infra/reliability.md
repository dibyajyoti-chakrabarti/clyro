# Infra Reliability Audit

## 1. ~~`Project.status` has no periodic reconciliation against real AWS state~~ — fixed

**Fixed as of commit `2cc6ac9`.** `backend/app/provisioning/reconcile.py` now implements a full sweep (`_check_connection`, `_resolve_stuck_deletion`, `sweep()`) wired into `CELERY_BEAT_SCHEDULE` (`backend/config/settings.py:96-101`, every 15 minutes) via `app.tasks.run_reconcile_sweep_task`, with test coverage (`ReconcileConnectionSweepTests`, `ReconcileStuckDeletionTests` in `backend/app/tests.py`). Marks dead `AWSAccountConnection`s (`health_status=UNREACHABLE`) and resolves stuck `Deployment.DELETING` rows exactly as described below. Re-verified live 2026-07-17. Original finding kept below for context.

### (superseded) original finding text

No Celery beat schedule exists anywhere in this codebase (`grep` for beat/periodic-task registration across `app/tasks.py` and `config/` finds nothing). `Project.status` is a one-way write — set on scan/build/deploy success or failure, `pause`/`resume`, and teardown — and is only ever re-checked against real AWS state when a user actively opens Step 5 (`deploy.health()`) or Step 4's provisioning screen (`deploy.poll()`). A project whose CloudFormation stack was deleted outside Clyro (manually in the AWS console, or by an account-level cleanup) keeps showing "Live" on the dashboard indefinitely until someone happens to open that project. Step 5 was hardened this cycle to honestly report "infrastructure not found" instead of hanging when that happens, which papers over the symptom but doesn't fix the stale dashboard state. A real fix needs new infrastructure (a Celery beat schedule + a lightweight `describe_stacks` sweep across live deployments) — sized as a dedicated piece of work, not a tweak.

**Confirmed live, 2026-07-15, attempting Phase 3's E2E run:** this isn't theoretical. Every `AWSAccountConnection` row in this dev environment's database (12 checked, across both connected AWS accounts, `321613317660` and `190084967282`) points at an IAM role that no longer exists — every bootstrap CFN stack that created these roles was torn down in AWS at some point, but not one of the corresponding DB rows was cleaned up. Concretely: `sts:AssumeRole` fails with `AccessDenied` for all of them, and 3 `Deployment` rows are permanently stuck in `status='deleting'` as a direct consequence — `teardown()`'s first step is `_assume()`, so a deployment whose connection's role is gone can never progress past `deleting`, with no path back to a terminal state through the app itself. This is the reconciliation gap in #1 above, but manifesting one level up the chain (the *connection*, not just the *stack*) and completely blocking any new live deploy in this environment until a fresh AWS connection is established.

**Partial mitigation, 2026-07-15:** `deploy._assume` now catches `AccessDenied`/`AccessDeniedException` specifically and raises a distinct `"Your AWS connection is no longer valid — reconnect your AWS account."` error instead of an opaque AssumeRole failure, so at least the symptom is diagnosable through the UI. An earlier attempt in the same session added a `role_exists()` pre-check using `iam:GetRole` on Clyro's *own* account before assuming — that doesn't work and was reverted: IAM `GetRole` is account-scoped and cannot see a role living in the customer's AWS account, so the check was silently a no-op (or worse, a false signal) rather than a real verification. There is still no way to distinguish "role deleted" from "role exists but the trust policy/permissions are wrong" via any AWS API short of attempting the assume itself — the actual reconciliation gap (no periodic sweep, no cleanup of dead `AWSAccountConnection`/stuck `deleting` `Deployment` rows) remains unfixed and is still the real piece of work here.

## 2. Stale "IacArchitect authors the template" documentation across 4 files

Per user decision this session: captured as an audit finding, not fixed in code. `cfn_generator.py` (deterministic, pure Python) is the actual sole author of Step 4's initial CloudFormation template today; `IacArchitect` (the deployed Bedrock AgentCore agent) is now scoped to `refine()` (user-directed NL edits) and a rare fallback fixer inside the lint/security correction loop — but four files still describe the old, superseded architecture as primary:

- `backend/app/provisioning/iac.py:4` — module docstring: *"The template is authored by the deployed IacArchitect runtime (generate + refine modes)"* — no longer true for `generate()`.
- `backend/app/provisioning/codebuild_spec.py:2` — *"the infrastructure IacArchitect generates"* — same stale framing.
- `backend/app/provisioning/build_spec.py:2` — *"the IacArchitect agent authors CloudFormation from"* — same.
- `backend/config/settings.py:141` — *"Deployed IacArchitect runtime that authors / refines the CloudFormation template... Required to generate or refine a template"* — `generate()` no longer requires this runtime at all in the common case (deterministic-first; the ARN is only consulted on the rare fallback path).

Risk: a future contributor reading these docstrings (rather than `iac.py`'s actual `generate()` body) will mis-model which system authors the template and where to make changes. Low effort to fix (comment/docstring updates only, no behavior change) whenever this file set is next touched for an unrelated reason.
