# Codebase Test Coverage Audit

## 1. `backend/app/provisioning/deploy.py` — mostly still zero test coverage

`deploy.py` (1262+ lines) is the actual state machine for `start`/`poll`/`teardown`/`recreate`/`pause`/`resume`/`update_live_stack`/`provision_with_feedback` — the highest-consequence code in the backend (it creates and destroys real AWS infrastructure). Nothing in the repo mocks/stubs `boto3` (no `moto`, no manual stubber), so `start`/`poll`/`teardown` themselves remain untested. One exception added this session: `_deterministic_template_fix` — the free-tier auto-fix table `provision_with_feedback` calls on a failed deploy — now has 3 tests (`DeterministicTemplateFixTests`) added after a live E2E run reproduced a real bug in it (see `audit/infra/reliability.md` — a paid-tier spec deployed to an AWS account AWS itself restricts to free-tier limits failed on both `BackupRetentionPeriod` and `DBInstanceClass` in turn, but the function only fixed whichever error CloudFormation happened to report first, exhausting the one bounded retry `provision_with_feedback` allows). Specific edge cases still worth unit coverage: the `create_stack` retry-on-race loop in `start()` (a rolled-back stack's delete racing a fresh create), the non-empty-bucket/ECR pre-empty step in `teardown()` (`_empty_undeletable_resources`), and `recreate()`'s `_has_been_live` gate (a bug here would let a rebuild destroy live customer data).

## 2. `backend/app/scanner/compliance.py` had zero tests before this session

Fixed this session — 10 tests now exist in `backend/app/tests.py`'s `ComplianceChecksTests`, covering the specific bugs found (workspace-monorepo lockfile-at-root, DB-less backend gating, multi-stage Dockerfile `AS` aliases, internal stage-name references, `models/__init__.py` package form, health-endpoint false-positive/package-include). Listed here only so this file doesn't silently regress back to zero — no further action needed unless new checks are added without tests.

## 3. `frontend/e2e/`'s four pre-existing specs never authenticate

`smoke.spec.js`, `landing.spec.js`, `auth.spec.js`, `navigation.spec.js` are all real, useful, and green, but none of them log in — `auth.spec.js` only confirms the login *page* renders and that unauthenticated `/app/dashboard` redirects to `/login`. None of the actual product (wizard, canvas, provisioning) has automated coverage. `frontend/e2e/provisioning.spec.js` (added this session) is a first attempt at closing this gap for the Step 1 → Step 4 → teardown path — the underlying flow it encodes was proven live end-to-end this session (interactively, via browser automation, not by running this checked-in spec file with `npx playwright test`), including catching and fixing a real deploy bug along the way. The spec itself is still unexecuted as a spec — its selectors were written from source reading, not verified against the live DOM, so treat it as a first draft to dry-run and fix up the first time someone actually runs it via the Playwright CLI.
